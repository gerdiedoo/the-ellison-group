# Admin platform implementation

## Discovered architecture

Next.js 15 App Router, React, TypeScript, pnpm, Tailwind/global CSS, Radix dialogs, React Hook Form/Zod, and the existing repository abstraction are retained. `app/` supplies server-rendered public/admin routes and API handlers. `components/` contains reusable public, search, property, form, and admin interfaces. Supabase provides Postgres, Auth and Storage in connected mode; the existing serialized JSON adapter supports key-free development. The existing Docker standalone build and Caddy configuration remain the deployment foundation.

The original site uses a warm paper/ink/sand palette, burgundy accent, Fraunces/Geist typography, square panels, hairline borders, editorial headings, local photography, and the existing wordmark. These carry into the expanded admin. Public Luxury Presence product descriptions informed practical CRM, lead-nurture, and handoff patterns. No authenticated Luxury Presence workspace was accessed and no proprietary branding/assets/interface were copied. See the [original audit](ADMIN-AUDIT.md).

## Persistence and database changes

`20261029064153_admin_platform.sql` adds compatible fields to `profiles`, `listings`, `leads`, and `showing_requests`; adds `pipeline_stages`, `lead_identities`, `lead_properties`, `activities`, `conversations`, `conversation_messages`, `tasks`, `automation_rules`, `automation_runs`, `notifications`, `message_templates`, and `campaigns`; and introduces scoped RLS and service-only transactional commands. Consent and audit history are not overwritten. Existing email aliases resolve to a canonical contact. Historical duplicate records are preserved rather than silently deleting their consent/audit relationships.

`20261029072719_platform_hardening.sql` adds AI reply references, property-reference arrays, scheduling exclusion, narrower profile/media access, direct REST restrictions for gated properties, immutable operation guards, and transaction-level duplicate workflow/chat protection. Property activity keeps its descriptive history when an eligible draft is deleted. Generated database definitions are in `lib/supabase/database.types.ts`.

Apply in the app's **development** environment with `pnpm exec supabase migration up --local`, then regenerate `pnpm db:types`. A production migration requires the normal environment-specific release/backup procedure. No production database was reset or deployed during this work.

The service-role key is used only by server modules after role and record checks. RLS also protects direct client database access. Direct anonymous/visitor access to CRM/conversations is denied; agents see assigned leads/conversations/tasks, linked properties, and permitted related records. Content settings and team changes require administrators. Real accounts use Supabase Auth; demo staff accounts require the configured access code on every login.

## Security and retention decisions

Sensitive routes validate the authenticated role and record assignment on the server. Legacy collection endpoints now enforce administrator-only content mutation and scoped lead/property reads/CSV export. Schemas validate inputs; CSV cells are escaped against formula execution. Origin checks, rate limits, payload limits, honeypot/Turnstile checks and secure cookies protect public mutations. File uploads require valid staff roles, MIME/signature agreement and bounded sizes. Provider errors are not returned verbatim. No server key is exposed as a public environment variable.

Public listing DTOs explicitly whitelist supported fields and public search attributes. Draft/archived records, private feed payloads, and gated full descriptions/galleries are excluded from public application responses. Lead gates are conversion controls; the existing Storage buckets serve public marketing photography, so they are not a DRM mechanism for already-public media URLs. Mock-store synchronous reads avoid exposing raw local JSON through development I/O promise-debug payloads. The mock store remains development-only single-process storage.

Standalone tracing explicitly excludes local mock records, uploads/logs and test reports. Runtime storage is provisioned separately; development contacts and test fixtures must not be copied into deployment output. Docker also excludes local data and private environment files from its build context.

`pnpm build` also runs `scripts/check-build.mjs`: it removes development-only trace entries and packaged copies after confirming the target is a generated standalone build inside this workspace. This covers Next 15's Windows exclusion-glob behavior. It never removes the original `.local` directory or its records.

Contacts, consent history, messages, and audit events are retained until an authorized operational retention procedure is applied. Archive instead of destroying linked transactions. The UI deliberately has no bulk purge or misleading “erase everything” action; legal holds, consent retention, provider copies and backups need an approved retention/deletion policy before live operation. No automatic destructive retention job was added.

## Metric definitions

- **New connections:** contacts created within the selected date range; repeated inquiries reuse their contact and do not inflate acquisition counts.
- **Qualified:** cohort contacts in open/won stages whose current order is third or later; lost outcomes are excluded. Stage ordering therefore affects this definition.
- **Lead → appointment:** distinct cohort contacts with a non-cancelled appointment whose scheduled start is in the selected range, divided by cohort contacts. Multiple appointments for one contact count once in the numerator.
- **Lead → conversion:** cohort contacts currently in a won-outcome stage divided by cohort contacts. These are current-outcome cohort rates, not historical snapshots.
- **Inventory / workload:** current permitted records; active means published and `for_sale` (including active rental offers); due follow-ups are open tasks with a due timestamp at or before now.
- **Property inquiries:** recorded inquiry events in the period. Inventory interest links represent distinct contact/property relationships.
- **Property views:** only actual `property_viewed` activities. No sample traffic is seeded and no new ingestion endpoint is claimed.
- **Chat:** conversations created in range and those linked to a captured contact. No inferred or simulated leads are counted.
